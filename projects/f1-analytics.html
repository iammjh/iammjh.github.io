01 / THE PROBLEM

One sport. Several kinds of data.

Season standings, session telemetry, and a fan’s saved interests have different data needs. The challenge is to make them feel like one application while keeping frequent updates and account-specific data under control.

My contribution

My work brings together the dashboard experience and backend workflows: protected accounts, saved watchlists, external race data, and the services that support updates.

02 / THE APPROACH

An application with a supporting service.

Next.js handles the interface, authentication, watchlists, and API routes. Prisma connects the application to MongoDB. A separate Node.js service supports polling, Redis caching, and email notifications.

03 / KEY DECISIONS

The details that shape the build.

01

Refresh according to context

The live dashboard uses a 15-second interval for live sessions and slows to five minutes when the tab is hidden. Recent, upcoming, and idle sessions have their own intervals.

02

Treat finished sessions differently

The telemetry route caches completed sessions for 24 hours and live sessions for 15 seconds. These are cache settings in the implementation, not measured response-time claims.

03

Keep personal data scoped to the user

Watchlist reads and writes require a session. Queries use the signed-in user’s ID, and creation validates the name and description before writing the record.

04 / THE RESULT

A working foundation for following the race.

The platform combines standings, results, telemetry views, authentication, and watchlists. The repository remains in active development, with room to extend the analytics experience.

A constraint worth understanding

The telemetry cache is process-local, so separate application instances do not share it. Data availability and refresh timing also depend on the upstream feeds.
